# T800 `waypoint_controller.py` 定位门控 + 心跳更新

> 依据 2026-10-31 GitHub `t800_navigation_ros1/main` 的控制器接口进行兼容性扩展。
> 未修改导航运动控制算法的 PID、航点列表结构、已有 Topic 名称和三个 Service 名称。

## 文件替换

- 将 `waypoint_controller.py` 复制到导航仓库 `scripts/waypoint_controller.py`（覆盖）。
- 将 `navigation_params_real.yaml` 复制到 `config/navigation_params_real.yaml`（覆盖前请比对自己最新调参）。
- 将 `navigation_params_sim.yaml` 复制到 `config/navigation_params_sim.yaml`（同上）。
- `config/waypoints_real.yaml` 保持 `frame_id: map`。
- **仿真 `config/waypoints_sim.yaml` 必须设置为 `frame_id: world`**，与 `gazebo_ground_truth.py` 的 `header.frame_id` 匹配。
- 实机和仿真 Launch 现有节点配置无需额外修改；Launch 已加载对应 YAML。
- 如采用 catkin 安装部署，检查 `CMakeLists.txt` 的 `catkin_install_python` 是否包含 `scripts/obstacle_detector.py`。

## 输入 Topic

| Topic | 类型 | 用途 |
|---|---|---|
| `~pose_topic`（实机 `/my_ros1/localization/base_footprint_pose`） | PoseStamped | `map` 中脚部 X、Y、Yaw；核验 `frame_id`、`header.stamp`、收包时间、数值 |
| `/my_ros1/localization/status` | String | 必须为 `ALIGNED_INITIAL_ONLY`，3 秒内收到更新 |
| `/my_ros1/localization/pose_status` | String | 必须为 `TRACKING_FIXED_GICP`，2 秒内收到更新 |
| `/my_ros1/navigation/obstacle_status` | String | 必须为当前目标的新鲜 `CLEAR` |

## 新增输出

`/my_ros1/navigation/controller_heartbeat`：`std_msgs/String`，**非 latch**，由 30Hz 控制循环产生，即使 `IDLE` 或故障锁定也持续发出。比如：

```text
seq=145|state=MOVE_FORWARD|enabled=1|motion_allowed=1|localization=READY|obstacle=CLEAR
seq=146|state=LOCALIZATION_FAULT_LOCKED|enabled=0|motion_allowed=0|localization=POSE_STATUS:STALE_ODOMETRY|obstacle=CLEAR
```

- `seq`：累计控制回调次数，仅用于观察是否仍执行。
- `enabled`：本控制器是否被人工启用，不等于正在输出非零速度。
- `motion_allowed`：本周期允许运动命令的门控结果（1/0）。
- `localization`：当前位姿/定位门控结果或报错原因。
- `obstacle`：当前航点对应的障碍检测状态。

**非常重要：** 心跳不代表下游可以直接把旧 Twist 继续发送。下游 ROS2 控制器至少应当：
1. 用自己的 `steady_clock` / 单调时钟记录最后一次**收到**心跳和 `Twist` 的时间。
2. 心跳超过 **0.3～0.5 秒**未收到、速度消息超过 **0.3～0.5 秒**未收到、`motion_allowed != 1`、消息解析失败或 Bridge 断链时，输出零速度或禁止运动。
3. 进程刚启动且尚未收到新的心跳、速度数据时，保持停止；拒绝使用旧命令。
4. 停车/失联是否需要更严格的人工复位，由 ROS2 运动接口和机器人厂商底层的安全机制决定。

**ROS1 Bridge 必须双向配置之外，额外桥接以下 ROS1→ROS2 Topic：**

```text
/my_ros1/motion/body_vel_cmd              geometry_msgs/Twist
/my_ros1/navigation/controller_heartbeat std_msgs/String
```

以上两项是下游 ROS2 运动控制侧的最小输入；定位状态和位姿在 ROS1 容器内部已经用于安全门控，并不要求为本功能桥接到 ROS2。

## 故障锁定逻辑

```text
启动（IDLE、默认禁止运动）
   |
   | 要求初次重定位成功、里程计追踪、实时新鲜位姿、当前航点障碍 CLEAR
   v
人工调用 /my_ros1/navigation/start
   |
   v
正常导航（原 ALIGN_HEADING / MOVE_FORWARD / ALIGN_FINAL_YAW）
   |
   | 任一定位状态异常、状态话题超时、位姿收不到、旧/未来时间戳等
   v
LOCALIZATION_FAULT_LOCKED -> enabled=0 -> 持续发送零速度
   |
   | 健康恢复后仍保持锁定；不会自动走
   v
人工再次调用 /my_ros1/navigation/start（且所有门控检查通过）
   |
   v
继续同一个航点，先从 ALIGN_HEADING 再对准目标
```

在 `WAIT_FOR_NEXT` 期间若发生定位故障，重授权后仍保持人工等候下一航点，不会绕过 `/next_waypoint`。

**与原逻辑相同**：障碍 `BLOCKED` 或一过性障碍通信异常时会暂停，清除后自动继续；只有**定位**故障采用人工重新授权。若实机还要求障碍故障后强制人工恢复，应在未来进一步调整控制策略。

## 验证命令

```bash
# ROS1 容器：先启动定位、FastGICP 完成重定位，再启动实机导航
roslaunch t800_navigation t800_navigation_real.launch
rostopic echo /my_ros1/navigation/controller_heartbeat
rostopic echo /my_ros1/navigation/state
rostopic echo -n 1 /my_ros1/localization/status
rostopic echo -n 1 /my_ros1/localization/pose_status
rostopic echo -n 1 /my_ros1/localization/base_footprint_pose
rostopic hz /my_ros1/navigation/controller_heartbeat
# 通过所有门控条件后人工启动
rosservice call /my_ros1/navigation/start '{}'
```

安全验证时先断开或屏蔽实际运动控制执行端：
- 首次未定位时调用 `/start`：应返回 `success: false`。
- 手动完成重定位和障碍检测清空后调用 `/start`：应允许启动。
- 模拟停止定位状态源/位姿源：应触发 `LOCALIZATION_FAULT_LOCKED` 且持续发布零速度。
- 恢复定位话题：仍保持锁定；再次手动调用 `/start` 才允许继续。
- 停止整个 `waypoint_controller` 进程：**ROS2 下游应在自己设定的超时内主动停止**，不能寄希望于 ROS1 发最后一帧零速度。

## 时间戳注意

消息 `header.stamp` 必须与当前 `rospy.Time.now()` 同属一个时钟域；当前允许最大 `pose_timeout=0.5s` 的延迟和 `pose_future_tolerance=0.1s` 的前向偏差。MID360s/FAST-LIO2 若使用不同步的设备时钟，定位即使正确也会被拒绝；应先同步时间或在源节点进行正确时间戳转换，而不是禁用时间检查。
